# Independent audit — 2026-09-20

Four independent auditors reviewed this branch: capacity arithmetic, gateway and
gate code, the deploy script, and the design's reasoning. None were told the
author's conclusions.

**Outcome: the central conclusion survives; most of the evidence for it did
not, and the implementation has defects that would have cost GPU hours and
produced a false "safe to serve" signal.**

Findings below were re-verified against the repo before being recorded here.
Severity is by consequence, not by effort to fix.

---

## 1. The claims that were wrong

### 1.1 `max-num-seqs` → 75 was dangerous advice — WITHDRAWN

`SYSTEM-DESIGN.md` §2.3 and §6 B1 argued `max-num-seqs: 512` is a ~6.8×
overcommit and should come down to ~75.

`K3-DEPLOYMENT.md:39` records **427 concurrent requests sustained** on this box,
and `K3-DEPLOYMENT.md:526` states plainly:

> `Maximum concurrency` is computed **assuming no prefix sharing** and is
> therefore pessimistic by ~5× for this workload. Ignore it.

**`redesign/capacity/` has no prefix-sharing term.** It bills every sequence
full price, which is exactly the error the source document warns against. Acting
on 75 risked a ~5× throughput cut.

The number is withdrawn. The *direction* may still be right — the box was
preempting at 512 — but the model cannot currently produce the right value.

### 1.2 The 8× was presented as a measurement; it is an inference

§2.2 divided an **8-GPU aggregate** (488 GiB) by a **per-rank** token count
(2,295,266). `RUNBOOK.md:154-156` shows both figures on adjacent lines of the
same per-worker log output:

```
Available KV cache memory: 61.06 GiB
GPU KV cache size: 2,295,266 tokens
Maximum concurrency for 262,144 tokens per request: 8.76x
```

61.06 GiB ÷ 2,295,266 = **27.9 KiB/token, per rank** — matching the documented
27 KiB almost exactly. The factor of 8 was inserted by the unit mismatch before
any physics was invoked.

"Two independent derivations agree" is false: 524e9 ÷ 2,295,266 = 228,296
exactly, so the "228 KB/token measured" cross-check is the same division
rearranged. There is **one** external constant in the entire capacity argument.

**The conclusion still holds** — MLA has one KV head, TP cannot shard it, and
vLLM's DCP documentation states the latent KV "is replicated in full across
every TP rank." De-duplication is still worth ~8× in aggregate. But it is a
physics argument, not a measurement of this box.

### 1.3 One constant, three measurements, two misses

The repo contains three `(available KV, reported pool)` pairs for the same model
at TP=8:

| source | available | pool | implied KiB/token |
|---|---|---|---|
| `K3-DEPLOYMENT.md:111` FULL_AND_PIECEWISE | 49.41 GiB | 1,169,808 | **44.3** |
| `K3-DEPLOYMENT.md:521` `max-model-len 12800` | 61.09 GiB | 1,696,278 | **37.8** |
| `RUNBOOK.md:154` current | 61.06 GiB | 2,295,266 | **27.9** |

The model fits the third and misses the other two by 64% and 40%. The reported
pool is a function of `max-model-len`, cudagraph mode and `max-num-seqs` — none
of which the model carries. A 3.2% residual against a quantity that moves 35%
under unrelated knobs is not evidence.

### 1.4 G2's pass criterion would record a correct win as a failure

§11 G2: *"Reported pool grows toward ~19M tokens."*

Under DP attention each rank still reports ~2.3M; only the aggregate across 8
ranks reaches ~18M. The criterion reads one rank's log line, sees "unchanged",
and §8 D2's tripwire converts that into "revert the engine decision."

Pass/fail must be **aggregate served tokens** or sustained concurrency, never
the per-rank pool line.

### 1.5 D2's "~7 points" rests on a premise the repo refutes

`redesign/gateway/__main__.py` applies `FOUNDRY_DEFAULT_MAX_TOKENS = 128_000` to
100% of 1,000 synthetic requests. `prod_stats.json` records
`client_max_tokens` p50 = **7,937**, p90 = 30,884, p99 = 200,000. Clients do not
send a fixed `max_tokens`, and none of the observed percentiles is 128,000.

§3.4 then subtracts that synthetic 7.0% from an observed 11.5% and names the
difference a real unexplained defect. The two are incommensurable.

Separately: of 108 failures, 27 are unauthenticated 401s and 13 are evalbot's.
The ~62 remaining 400s belong to the single key that is 92% of traffic. This is
one developer's client configuration reported as a production defect.

### 1.6 Decode was dismissed with the wrong denominator

§6 C3/C4 and §8 D2 dismiss decode-side work as "sub-1% end-to-end" because the
workload is 97.7% input **tokens**. From `prod_stats.json`:

```
prefill p50  1.10 s        decode p50  33.25 s        e2e p50  46.21 s
```

Decode is **~72% of end-to-end latency**. The token ratio is the right
denominator for *memory* and the wrong one for *latency*. An 8.9% KDA
fused-decode improvement is ~8.9% of 33 s, not sub-1%.

### 1.7 P1 never fires

`python3 -m redesign.gateway` reports P0 69%, P2 31%, **P1 0%** —
`ShortChatRule` requires `not has_tools`, and tool use is pervasive
(`tool_call_parser_invocations_total` = 81,356 over 494 requests). D1 and D4
are decisions about a class with no members.

### 1.8 The prefix-cache "collapse" is one of two disagreeing numbers

§3 reports 6–13% marginal from two 60-second windows. `prod_stats.json` reports
`prefix_cache_hit_rate` = **0.4927** cumulative over the same engine lifetime.
The design never mentions the 49% figure. The cumulative counter is
warmup-polluted — but two 60-second windows are equally not a steady-state
measurement, and the entire eviction-spiral narrative descends from them.

### 1.9 "Idempotent" is false

`stage_done()` (`deploy.sh:83`) is **dead code** — defined, never called. The
markers are written and never read. Re-running `engine` unconditionally
`docker rm -f`s a live engine.

## 2. Deploy defects that would have halted the first run

Each of these aborts with the GPU billing.

| # | Defect | Consequence |
|---|---|---|
| **D-1** | `--model-path` points at the HF cache *container* dir, not the snapshot — no `config.json` there | Engine exits instantly; `verify` then waits the full 15 min. ~1 h download + 15 min of 8×MI355X to find a path string |
| **D-2** | `edge` writes an nginx config referencing a cert that does not exist, then runs `certbot --nginx`, which test-reloads nginx | certbot aborts; a broken `k3.conf` is left behind so every later `nginx reload` also fails |
| **D-3** | `keys` runs before `edge` and writes to `/etc/nginx/conf.d` with no nginx installed | Aborts after the engine is up and billing. `stage_keys` also never calls `mark_done` |
| **D-4** | Re-running `engine` kills a live engine with no guard | Cold reload outage on a stage documented as free; VRAM may not be released before the restart |
| **D-5** | `verify` overwrites the golden correctness baseline every run | A baseline recorded from an fp8 engine makes every later `--compare` pass against garbage, **silently** |

## 3. Security

| # | Defect | Consequence |
|---|---|---|
| **S-1** | `limit_req_zone`/`limit_conn_zone` are keyed on `$k3_customer`, empty for unauthenticated traffic — nginx does not account empty keys | **Anonymous clients are entirely unthrottled.** Credential stuffing and connection floods are free. Open-internet outage vector |
| **S-2** | `limit_conn 200` per customer against a 75-slot engine | One customer can occupy every slot |
| **S-3** | `X-K3-Batch` is client-supplied and `BatchHintRule` is first | Class is self-declared. A batch workload that omits the header lands in P0. (The customer header is *not* forgeable — nginx overwrites it. That part is correct.) |
| **S-4** | `HF_TOKEN` printed in cleartext by `--dry-run` | The docs instruct operators to run `--dry-run` first; the token lands in scrollback and CI logs |
| **S-5** | `customers.tsv` created 0644 under `/scratch` 0755 | Bearer tokens world-readable |
| **S-6** | Customer table is interpolated into nginx `map` unescaped | A `"` in either field injects arbitrary directives — e.g. a `default` mapping that authenticates everyone |
| **S-7** | Missing customer table produces an empty map and a reload, behind a `WARN` | A routine `./deploy.sh keys` takes every customer offline while printing `OK` |
| **S-8** | Gateway unit runs as root, no `User=`/`NoNewPrivileges`/`ProtectSystem` | Root executes repo code |

## 4. Gateway defects (reproduced against a running server)

| # | Defect | Measured |
|---|---|---|
| **G-1** | `engine.py` uses `response.read(8192)`, which blocks for the full 8 KB | First SSE byte reached the client after **7.14 s** with the engine emitting from 0.02 s. P0's 3 s target is blown on every streaming request — and `observe_ttft` times the delayed write, so the metric reports the corrupted value as truth |
| **G-2** | Client disconnect mid-stream never releases the slot | `in_flight` stuck at 1 indefinitely; engine keeps generating. Class wedges at its limit and 429s forever |
| **G-3** | `ClassBudget` has no lock | 16 threads, balanced acquire/release: **19 slots permanently leaked** in the worst of 20 trials. Lost decrements never recover |
| **G-4** | `LatencySeries` keeps samples sorted and `pop(0)`s — evicting the **smallest**, not the oldest | After one incident, p50/p95 pinned at the incident value through 100,000 healthy requests. This is the metric G2's regression criterion reads |
| **G-5** | Non-dict JSON body kills the handler thread with no response | Array/number/string bodies close the connection with no HTTP response; `null` pins the thread until client timeout |
| **G-6** | Only `OSError` is caught around the relay; `IncompleteRead` is not | Engine dying mid-response yields **HTTP 200 with a truncated body and no terminating chunk** |
| **G-7** | `/metrics` scraped synchronously on every request; `_last_preemptions` races | Extra round trip on the hot path; "per minute" is actually a per-request delta; threshold 0.0 makes shedding a one-shot flap |
| **G-8** | Token estimator under-counts | 250k CJK chars → estimated 71,433 (real ~250,000) → **engine 400**, the exact failure the clamp exists to prevent. 1.2 MB base64 image → estimated **7**, classified P1. `tool_calls` and integer token-id prompts count as 0 |
| **G-9** | `max_completion_tokens` not clamped; `n`/`best_of` ignored | Upstream request carries both fields with the unclamped one intact |
| **G-10** | No socket timeout, no thread cap, 64 MB buffered per thread | Slowloris pins threads indefinitely |

## 5. The gate cannot detect what it claims to detect

This is the most serious category: a gate that licenses a bad deploy has no
downstream recovery.

| # | Defect | Evidence |
|---|---|---|
| **Q-1** | `--long-context` with no values runs **zero checks** and exits 0 | `python3 -m redesign.gate --tier 3 --long-context --url http://127.0.0.1:1` → `GATE PASS 0 checks`, exit 0, against a dead engine |
| **Q-2** | `CleanText` never compares output to the expected answer, and `and not c.isprintable()` lets all printable Unicode through | `'the sky is green and 2+2=5'` passes; mojibake passes |
| **Q-3** | `NoDegenerateRepetition` only compares adjacent identical words | `'the cat sat. ' × 200` passes; only `'the ' × 60` fails — the one pattern the test covers |
| **Q-4** | `ExactAnswer` matches anywhere in the completion, and "12" appears in the syllogism prompt | `'I cannot answer this question. The premise mentions 12 Blips.'` passes |
| **Q-5** | Tier 3 assumes 4 chars/token; the filler is ~6.7 | `needle-128k` builds ~77k real tokens — under 30% of the window, never reaching the regime fp8 changes |
| **Q-6** | The haystack is one sentence repeated, with no distractors | Trivially retrievable; repetitive filler is what KV compression handles best |
| **Q-7** | `client.py:86` reads `choice["message"]` outside the `try` | A `/v1/completions`-shaped response crashes the whole gate run |

## 6. What the tests were worth

117 passing tests, and the pure decision logic (classification, clamp
arithmetic, off-box budget semantics) is genuinely covered. Everything else is
circular or absent:

- **No concurrency tests at all**, in modules whose docstrings claim thread safety.
- `test_server.py` feeds `LatencySeries` a monotonically increasing sequence —
  the one construction where G-4 is invisible.
- `test_multimodal_content_parts_are_counted` tests a **text** part, not an image.
- No streaming test anywhere; G-1, G-2, G-6, and the header defects all live on
  the SSE path.
- `test_gate.py`'s mock returns the correct answer keyed on a prompt substring,
  so the healthy tests verify the regex rather than the check. Its negative tests
  use the exact patterns the checks were written against — which is why Q-2
  through Q-4 survive a suite whose docstring says "the important tests are the
  negative ones".

The suite guards refactors, not correctness.

## 7. What survives

- **MLA KV replication under TP.** Confirmed at primary source in both engines'
  documentation. The A1 lever is real and worth roughly the TP size in aggregate.
- **Z2's engine finding.** A1 and A2 are reachable on SGLang and not on
  vLLM/ROCm today. Not challenged by any auditor.
- **§1.1's single-replica arithmetic.** 1.5 TB / 8 = 187.5 GB = 65% of 288 GB;
  3 TB > 2.3 TB rules out P/D disaggregation. Internally consistent.
- **§3.3 and §3.4's epistemic discipline** — naming the sample-size problem and
  refusing to claim D2 recovers 11.5% — were singled out by two auditors as the
  strongest parts of the document. The failure was abandoning that discipline in
  the bolded summary rows a reader actually quotes.
- **The clamp arithmetic itself.** No auditor could construct an input where
  `prompt + granted > window` *given a correct prompt count*. The hole is the
  estimator (G-8), not the clamp.
- **The shell.** `bash -n` clean, shellcheck clean but for 4 cosmetic hits, no
  `set -e` abort hazard.

## 8. Order of work

1. **Gate Q-1** — it exits 0 having run nothing. Everything else is recoverable;
   a gate that licenses a bad deploy is not.
2. **Deploy D-1, D-2, D-3** — three sequential first-run aborts with the meter
   running.
3. **G-1 + G-2** — same root cause, both certain, both customer-visible.
4. **G-3** — silent permanent wedge.
5. **S-1** — open-internet DoS before the edge takes public traffic.
6. **D-4, D-5** — state corruption rather than loud failure.
7. **Withdraw B1's number**; add a prefix-sharing term before re-deriving it.
8. **Fix G2's pass criterion** (§1.4) before booking the session.
9. Restate §2 per-rank throughout; reinstate G0.
10. The rest of the gate (Q-2..Q-7), then G-4 onward.
