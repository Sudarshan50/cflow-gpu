# SECRETS — credential inventory and handling

Every credential on this box: where it lives, what it opens, how to rotate it,
and what to do when one leaks.

**No real credential value appears in this document, and none should ever
appear in any other.** Refer to credentials by file path. Formats are shown as
patterns (`sk-k3-<name>-<40 hex>`); values are not shown at all. Do not `cat` a
secret file into a terminal you are sharing, a ticket, a commit message, or a
chat message — the comparison and audit commands below are written to avoid it.

Related: [`ARCHITECTURE.md` §3](ARCHITECTURE.md) explains *why* there are two
tiers of API credential; [`RUNBOOK.md` §4](RUNBOOK.md) covers customer
onboarding and revocation as day-2 tasks; [`DEPLOY.md` §4.3](DEPLOY.md) covers
first-time generation on a new box.

## 1. Inventory

Eight credentials. Four live in the repo directory on `/scratch` (ephemeral),
four live outside it.

| Path | Authenticates | Format | Mode / owner | Generated by | Blast radius if leaked | Rotation |
|---|---|---|---|---|---|---|
| `/scratch/deploy/api-key.txt` | nginx → vLLM (the single upstream credential vLLM enforces as `--api-key`) | `sk-k3-<48 hex>` (`deploy.sh:406-408`) | `600 root:root` | `deploy.sh` secrets stage, `openssl rand -hex 24` | Inference against vLLM **from the box only** — it binds loopback, and the public edge rejects this key with 401 because it is not in the customer map (`verify-auth.sh:73-75`). Combined with any shell on the box it also opens the endpoints `--api-key` does not guard. | §4.2 — needs a vLLM restart |
| `/scratch/deploy/vllm-k3.env` | same credential, as `VLLM_API_KEY`, plus the (non-secret) AITER flags | `VLLM_API_KEY=sk-k3-<48 hex>` | `600 root:root` | `deploy.sh:422-451`, from `vllm-k3.env.example` | Same as `api-key.txt` — it is the same value in a second place | §4.2 (rotated together, always) |
| `/scratch/deploy/customers.tsv` | every customer → nginx | `<name>\t sk-k3-<name>-<40 hex>`, tab-separated (`gen-keys.sh:49-50`, `customers.tsv.example:3`) | `600 root:root` | `gen-keys.sh add <name>` | **The worst one.** Full inference through the public endpoint as any customer, up to that customer's caps, attributed to and billed to them. The whole file is every customer at once. | §4.1 per customer |
| `/etc/nginx/conf.d/00-k3-keys.conf` | — (generated) | nginx `map` containing **every customer key in cleartext** (`gen-keys.sh:66-94`) | `640 root:root` | `gen-keys.sh` | Identical to leaking `customers.tsv` | Regenerate: `./gen-keys.sh` |
| `/etc/nginx/conf.d/k3-limits.inc` | — (generated) | limit directives plus `proxy_set_header Authorization "Bearer <upstream key>"` **in cleartext** (`gen-keys.sh:97-112`) | `640 root:root` | `gen-keys.sh` | Identical to leaking `api-key.txt` | Regenerate: `./gen-keys.sh` |
| `/scratch/deploy/dash-password.txt` | operator → dashboard, cleartext password for basic-auth user `admin` | 20 chars base64, `openssl rand -base64 15` (`deploy.sh:416-417`) | `600 root:root` | `deploy.sh` secrets stage | Read access to the dashboard: per-customer usage and identities, traffic volumes, GPU telemetry, cert expiry. **No inference and no key values** — the dashboard reads `api-key.txt` only to call `/v1/models` and never puts it in a response (`dashboard/server.py:529-543`) | §4.3 |
| `/etc/nginx/k3-dash.htpasswd` | the same, as the hash nginx checks | `admin:$apr1$<salt>$<hash>` | `640 root:www-data` | `deploy.sh:473-482`, `openssl passwd -apr1` | Offline cracking of the dashboard password | §4.3 (regenerated from `dash-password.txt`) |
| `/etc/letsencrypt/live/cflox.store/privkey.pem` (symlink → `/etc/letsencrypt/archive/cflox.store/privkey1.pem`) | the server to TLS clients | ECDSA private key, PEM (`key_type = ecdsa` in the renewal config) | `600 root:root` | certbot, via `issue-cert.sh` | Impersonation of `cflox.store` to anyone whose traffic can be intercepted, and decryption of captured sessions that did not use forward secrecy. Does **not** by itself grant API access | §4.4 |

Two things that are *not* secrets and are often mistaken for them: the
`k3usage` access log (customer **names**, paths, IPs — no keys) and
`/etc/nginx/conf.d/k3-tls.conf` (policy, no credentials).

### 1.1 The two tiers, in one paragraph

Customers present their **own** key. nginx maps it to an identity, applies that
identity's quotas, logs it, and then **replaces** the `Authorization` header
with the single upstream credential that vLLM knows
(`gen-keys.sh:105-110`). vLLM only ever sees one key. That is why customer keys
cost an nginx reload to add or revoke, while the upstream key costs a ~6-minute
vLLM restart — and why the upstream key is useless to an outsider: presenting
it at the edge is a 401, which `verify-auth.sh:73-75` asserts deliberately.

## 2. Why none of it is in git

`.gitignore` lists every cleartext credential, with the reason inline
(`.gitignore:1-31`):

| Entry | Line | What it protects |
|---|---|---|
| `api-key.txt` | 10 | upstream credential |
| `dash-password.txt` | 13 | dashboard password |
| `customers.tsv` | 16 | every live customer key |
| `vllm-k3.env` | 20 | `VLLM_API_KEY` alongside the AITER flags |
| `nginx/00-k3-keys.conf`, `nginx/k3-limits.inc` | 24-25 | the generated fragments, if anyone copies them into the repo for review |
| `*.htpasswd` | 26 | any basic-auth hash file |
| `secrets/`, `*.pem`, `*.key` (with `!**/*.pub`) | 29-32 | anything a future script drops in, and any key material pasted in by hand |

Every ignored file has a committed `*.example` twin, so the *shape* is
reviewable without the value:

| Real file (ignored) | Committed twin |
|---|---|
| `vllm-k3.env` | `vllm-k3.env.example` — real AITER flags, `VLLM_API_KEY=sk-k3-REPLACE_ME` |
| `customers.tsv` | `customers.tsv.example` — format, helper usage, an all-zero placeholder key |

**The generated nginx fragments are never committed in any form.**
`00-k3-keys.conf` and `k3-limits.inc` live only in `/etc/nginx/conf.d/`, are
rebuilt from `customers.tsv` and `api-key.txt` by `gen-keys.sh`, and their
reviewable counterpart is the generator itself. The same pattern applies to
`k3-tls.conf`, whose reviewable copy is `nginx/k3-tls.conf.template` — that one
contains no credentials, which is why a template can exist at all.

`.gitignore:6` tells you to verify with `make secret-scan` before every push.
That target exists (`Makefile:23-24`) and runs `./secret-scan.sh`; see §7.

## 3. Provisioning a new box

`/scratch` is ephemeral: the repo, the weights, and every credential in the
table above that lives under `/scratch/deploy` are destroyed when the droplet
is reclaimed (`ARCHITECTURE.md` §9). Decide deliberately what to carry.

| Credential | Fresh or carried | Why |
|---|---|---|
| `api-key.txt` + `vllm-k3.env` | **fresh** | Only nginx holds it. Regenerating it is invisible to customers, and `deploy.sh` mints one automatically if the file is absent (`deploy.sh:404-409`). |
| `customers.tsv` | **carried** | These are keys your customers have already configured. Losing the file means re-issuing every key and breaking every live integration at once. Copy it to the new box **before** running `./deploy.sh keys`, mode 600. |
| `dash-password.txt` + htpasswd | **fresh** | Internal credential, nobody else depends on it. |
| TLS key and certificate | **fresh** | certbot issues a new one; the old private key should not travel. Note the DNS gate and rate limit in §4.4. |
| `00-k3-keys.conf`, `k3-limits.inc` | **regenerated** | `./gen-keys.sh` rebuilds both from `customers.tsv` + `api-key.txt`. Never copy them between boxes. |

Two compatibility details that make a carried `customers.tsv` actually work:

- **The served-model alias must survive.** `config.yaml:10-15` keeps `kimi-k3`
  alongside `FW-Kimi-K3` because live customer integrations still send the old
  name, and dropping it 404s them. A rebuild that quietly drops the alias
  breaks the same clients whose keys you carefully preserved.
- **The public name and path must survive.** Customers are configured against
  `https://cflox.store/v1`; anything that changes the hostname is a customer
  migration, not a rebuild.

Order matters on the new box: secrets before keys (`gen-keys.sh:20` reads
`api-key.txt` and bakes it into `k3-limits.inc`), keys before TLS (the TLS block
references `$k3_customer` and includes `k3-limits.inc`, so `nginx -t` fails
without them). `deploy.sh` encodes the full ordering with the reasons
(`deploy.sh:191-228`).

## 4. Rotation runbooks

### 4.1 A customer key — nginx reload only

Fastest path, with a gap in service for that customer between the two reloads:

```bash
cd /scratch/deploy
./gen-keys.sh revoke <name>
./gen-keys.sh add <name>          # prints the new key ONCE
```

Make-before-break, if the customer cannot take a gap: mint `<name>-2`, deliver
it, watch their traffic move in `/var/log/nginx/k3-usage.log`, then revoke
`<name>`. Details and caveats in [`RUNBOOK.md` §4.5](RUNBOOK.md).

- No vLLM restart. Ever. This is the entire point of the two-tier model
  (`gen-keys.sh:107-109`).
- `gen-keys.sh` runs `nginx -t` itself and reloads only if it passes
  (`gen-keys.sh:117-121`), so a failed rotation leaves the previous map serving.
- Deliver the key over a channel you would be willing to use for a password.
  It is printed once, to stdout (`gen-keys.sh:52-53`); do not paste it into a
  ticket that outlives the rotation.

### 4.2 The upstream key (`api-key.txt` + `VLLM_API_KEY`) — needs a vLLM restart

**Read this before starting: the two copies must match exactly, and the
mismatch failure is silent at the edge.** If `VLLM_API_KEY` != `api-key.txt`,
nginx authenticates the customer, swaps in a credential vLLM rejects, and
**every request 401s *after* passing nginx** (`DEPLOY.md` §8.7,
`vllm-k3.env.example:19-23`, `deploy.sh:430-431`). From the client side that is
indistinguishable from a revoked key; the tell is a usage-log line with a
populated `cust=` and `status=401`.

There are three copies of this value in total — `api-key.txt`, `vllm-k3.env`,
and the `proxy_set_header` line baked into `k3-limits.inc` at generation time
(`gen-keys.sh:20`, `:110`). All three must move together.

Sequence, ordered to confine the outage to the restart that is unavoidable
anyway:

1. Write the new value into `api-key.txt` at mode 600. The shape
   `deploy.sh:406-408` generates is `sk-k3-` plus 48 hex:
   ```bash
   cd /scratch/deploy
   umask 077 && printf 'sk-k3-%s\n' "$(openssl rand -hex 24)" > api-key.txt
   chmod 600 api-key.txt
   ```
2. Propagate it into `vllm-k3.env` — use the script rather than an editor, so
   the AITER flags cannot drift and the file keeps exactly one `VLLM_API_KEY`
   line (a duplicate is an invisible override; `deploy.sh:432-434`):
   ```bash
   ./deploy.sh secrets
   ```
3. Confirm the two agree, without printing either:
   ```bash
   cmp -s <(sed -n 's/^VLLM_API_KEY=//p' vllm-k3.env | tail -1) \
          <(tr -d '\r\n' < api-key.txt) && echo match || echo MISMATCH
   ```
4. Restart the engine. This is a ~6-minute customer-visible outage
   (`RUNBOOK.md` §2.2):
   ```bash
   systemctl restart k3.service
   ```
5. **While it loads**, rebuild the nginx layer so the new key is in
   `k3-limits.inc` by the time the engine answers:
   ```bash
   ./gen-keys.sh
   ```
6. Verify:
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8001/health   # 200 when loaded
   make verify                                                            # ALL CHECKS PASSED
   ```

If you do step 5 long before step 4, you extend the 401 window; if you skip it
entirely, the endpoint 401s indefinitely while every individual file looks
correct. `deploy.sh` also detects the mismatch at startup and dies with the
exact remedy rather than hanging (`deploy.sh:697-699`).

No model or environment change is involved, so the correctness gate is not
required — but running `make gate` after any restart is the standing rule
(`Makefile:6`).

### 4.3 The dashboard password

```bash
cd /scratch/deploy
umask 077 && openssl rand -base64 15 > dash-password.txt
chmod 600 dash-password.txt
./deploy.sh secrets        # regenerates the apr1 htpasswd, 640 root:www-data
```

`deploy.sh` reproduces the stored hash from its own salt to decide whether the
htpasswd already encodes the current password, and only regenerates when it
does not (`deploy.sh:459-482`) — so this is safe to re-run and does not churn
the salt needlessly. nginx reads the htpasswd at request time as the `www-data`
worker, which is exactly why that file is group `www-data`
(`deploy.sh:453-456`); a reload is not required, though one is free if you want
certainty:

```bash
nginx -t && systemctl reload nginx
curl -s -o /dev/null -w '%{http_code}\n' --resolve cflox.store:443:127.0.0.1 https://cflox.store/   # 401 without credentials
```

### 4.4 The TLS private key

Routine renewal keeps the same key material only if certbot is configured to
reuse it; by default each renewal generates a new key, and no action is needed
from you. Renewal is `certbot.timer`'s job — see [`RUNBOOK.md` §8](RUNBOOK.md),
including the **gap that nginx is not reloaded after renewal**, which applies
to a rotation just as much as to a renewal.

To replace the key deliberately (after a suspected compromise):

1. Force a re-issue with fresh key material:
   ```bash
   certbot certonly --webroot -w /var/www/certbot -d cflox.store -d www.cflox.store \
     --force-renewal --non-interactive --agree-tos -m admin@cflox.store
   ```
2. Reload nginx so the running process picks it up — it will otherwise keep
   serving the old certificate from memory:
   ```bash
   nginx -t && systemctl reload nginx
   openssl s_client -connect 127.0.0.1:443 -servername cflox.store </dev/null 2>/dev/null \
     | openssl x509 -noout -enddate -serial
   ```
3. Revoke the old certificate if the key is believed compromised
   (`certbot revoke --cert-path /etc/letsencrypt/archive/cflox.store/certN.pem`),
   choosing the archived certificate that corresponds to the retired key.

**Do not loop on failures.** A failed HTTP-01 burns Let's Encrypt rate limit at
**5 failures per hostname per hour**, which is why `issue-cert.sh` gates on a
public resolver returning `EXPECT_IP` before calling certbot at all
(`issue-cert.sh:4-5`, `:20-34`). Prefer `./issue-cert.sh` for ordinary
issuance; it keeps that gate, backs up the TLS block, and rolls back if
`nginx -t` fails (`issue-cert.sh:133-138`).

### 4.5 The generated nginx fragments

They are not rotated independently — they are **derived**. Any change to
`customers.tsv` or `api-key.txt` is applied by:

```bash
./gen-keys.sh
```

Never hand-edit them. The header they carry says so
(`gen-keys.sh:68-69`: "GENERATED by gen-keys.sh - do not edit by hand"), and the
next run of the generator silently discards anything you added.

## 5. File permission expectations

Two different rules, for two different readers, and the distinction is the
reason they differ:

- **`600 root:root` — cleartext secret files.** `api-key.txt`,
  `dash-password.txt`, `customers.tsv`, `vllm-k3.env`, and the TLS private key.
  Only root processes read these. `gen-keys.sh:66` and `deploy.sh:398` set
  `umask 077` around the writes so nothing lands wider even momentarily.
- **`640` — files nginx reads.** With the group chosen by *which* nginx process
  reads them:

  | File | Expected | Read by |
  |---|---|---|
  | `/etc/nginx/conf.d/00-k3-keys.conf` | `640 root:root` | the **master** at config load, which runs as root — the worker user never needs them, which is exactly the rationale at `gen-keys.sh:64-65` |
  | `/etc/nginx/conf.d/k3-limits.inc` | `640 root:root` | same |
  | `/etc/nginx/k3-dash.htpasswd` | `640 root:www-data` | the **worker**, at request time, and `nginx.conf:1` sets `user www-data` — hence the group (`deploy.sh:453-456`) |

Audit all of them in one line (prints modes and owners, never contents):

```bash
stat -c '%a %U:%G %n' \
  /scratch/deploy/api-key.txt /scratch/deploy/dash-password.txt \
  /scratch/deploy/customers.tsv /scratch/deploy/vllm-k3.env \
  /etc/nginx/k3-dash.htpasswd \
  /etc/nginx/conf.d/00-k3-keys.conf /etc/nginx/conf.d/k3-limits.inc \
  "$(readlink -f /etc/letsencrypt/live/cflox.store/privkey.pem)"
```

Expected output, and what was observed on 2026-09-18:

```
600 root:root /scratch/deploy/api-key.txt
600 root:root /scratch/deploy/dash-password.txt
600 root:root /scratch/deploy/customers.tsv
600 root:root /scratch/deploy/vllm-k3.env
640 root:www-data /etc/nginx/k3-dash.htpasswd
640 root:root /etc/nginx/conf.d/00-k3-keys.conf
640 root:root /etc/nginx/conf.d/k3-limits.inc
600 root:root /etc/letsencrypt/archive/cflox.store/privkey1.pem
```

Anything group- or world-readable that is not in the 640 rows above is a
finding. `gen-keys.sh:51`, `:95`, `:112` and `deploy.sh:411`, `:420`, `:451`,
`:479`, `:495` are the places that set these, so a drifted mode usually means
a file was created by hand rather than by a script — re-running
`./deploy.sh secrets` and `./gen-keys.sh` restores them.

## 6. Leak response

Work top to bottom; each step is ordered by how much damage it stops per minute
spent.

### 6.1 A single customer key leaked

1. **Revoke it now.** `./gen-keys.sh revoke <name>` — effective on the reload
   the script performs, seconds later. No engine restart, no impact on other
   customers.
2. **Assess use.** Grep the usage log for that identity and look for requests
   you cannot account for (unfamiliar `ip=`, off-hours volume, unusual paths):
   ```bash
   grep "cust=<name> " /var/log/nginx/k3-usage.log | tail -200
   ```
3. **Re-issue** under a new name (`./gen-keys.sh add <name>-2`) and deliver it
   over a channel that is not the one that leaked.
4. **Tell the customer** what was exposed and when.

### 6.2 The upstream key leaked

Lower urgency than it feels, because it is not usable from off-box: vLLM binds
loopback (`config.yaml:106`) and the edge rejects this key with 401
(`verify-auth.sh:73-75`). Treat it as urgent only if the box itself may be
compromised — in which case go to §6.4.

1. Rotate per §4.2, scheduling the ~6-minute restart.
2. Check for direct-to-engine use that bypassed the edge: requests served by
   vLLM but absent from `/var/log/nginx/k3-usage.log` (which is written only
   from the `/v1/` location, `issue-cert.sh:79`) came from on the box.

### 6.3 The repo or a credential was pushed to GitHub

1. **Assume every credential in that push is burned**, including ones you think
   were partially redacted. Rotate them: customer keys (§4.1) first, then the
   upstream key (§4.2), then the dashboard password (§4.3).
2. **Delete the published copy** — but understand that deleting the file in a
   new commit does **not** unpublish it. The blob remains reachable in history
   and in any fork or cache.
3. **Rewrite history or start a fresh one.** `secret-scan.sh:155-158` states the
   two options: `git checkout --orphan` for a clean start, or `git-filter-repo`
   to excise the blob. Rotation is required either way.
4. Re-run `make secret-scan` and confirm the history scan is clean before
   pushing anything again.

### 6.4 The box is compromised

1. **Cut off customer traffic** before anything else: `systemctl stop nginx`.
   The engine keeps running on loopback, which is fine — nothing off-box can
   reach it.
2. **Preserve evidence**: copy `/var/log/nginx/k3-usage.log`,
   `/var/log/nginx/error.log`, `journalctl -u k3.service`, and
   `docker logs k3` off the box. Note that `docker logs` is destroyed on the
   next engine restart (`k3.service:29`, `RUNBOOK.md` §7.1).
3. **Treat every credential in §1 as burned**, including the TLS private key.
4. **Rebuild rather than clean.** The design assumes the box is disposable and
   the repo is the durable copy (`ARCHITECTURE.md` §9). Follow
   [`DEPLOY.md`](DEPLOY.md), generating everything fresh — including
   `customers.tsv`, which in this one case must **not** be carried over: those
   keys were on the compromised box. Every customer gets a new key.
5. Revoke the TLS certificate (§4.4 step 3) so the old key cannot be used to
   impersonate the domain.

## 7. Pre-push checklist

Run this before every push. It is a script, not a habit, for a reason stated at
`secret-scan.sh:4-7`: **`.gitignore` only stops a file from being *added*. It
does nothing for a file that was already committed**, and `git push` will
happily publish a key that was staged once and ignored afterwards.

```bash
make secret-scan          # = ./secret-scan.sh   (Makefile:23-24)
./secret-scan.sh --staged # fast subset, suitable for a pre-commit hook
```

Exit 0 means safe to push; exit 1 means do not. Five phases
(`secret-scan.sh:56`, `:66`, `:76`, `:106`, `:128`):

| Phase | Checks |
|---|---|
| tracked-file check | none of `api-key.txt`, `dash-password.txt`, `customers.tsv`, `vllm-k3.env`, `nginx/00-k3-keys.conf`, `nginx/k3-limits.inc` is tracked (`secret-scan.sh:27-34`) |
| ignore-rule check | every one of those that exists on disk is actually ignored |
| content scan | tracked **and staged** content against the credential patterns below |
| literal live-value scan | the **actual** values from `api-key.txt`, `dash-password.txt`, `vllm-k3.env` and `customers.tsv`, matched literally against staged content (`secret-scan.sh:101-124`). This is what catches a credential that does not look the way the patterns expect — the dashboard password in particular matches no pattern. Values shorter than 12 characters are skipped as too noisy, and a finding prints only the first 8 characters, never the value |
| history scan | the patterns across `git rev-list --all` — the phase that catches a key committed once and ignored later (`secret-scan.sh:128-145`) |

Patterns (`secret-scan.sh:41-48`): this deployment's key prefix
`sk-k3-[a-z0-9_-]*-[0-9a-f]{40}`, generic `sk-` keys, PEM private-key headers,
`$apr1$` hashes, GitHub tokens, and `VLLM_API_KEY=sk-k3-` other than the
`REPLACE_ME` placeholder. Documented placeholders — `REPLACE_ME`, `<name>`,
`<40 hex>`, forty zeroes, `REDACTED` — are excluded so the scan does not cry
wolf on this file or on the `*.example` twins (`secret-scan.sh:50`).

A concrete manual check for the `sk-k3-` prefix, if you want one without the
script — note it scans **committed and staged content**, not the working tree,
because the real secret files are ignored and would match by design:

```bash
git grep -nIP 'sk-k3-[a-z0-9_-]*-[0-9a-f]{40}' --cached
git grep -nIP 'sk-k3-[a-z0-9_-]*-[0-9a-f]{40}' $(git rev-list --all)
```

Both should print nothing. If the second one prints anything, **rewriting
history is mandatory and rotation is mandatory** — see §6.3. Deleting the file
in a follow-up commit does not help.
